# 新成员审查

你是刚看到这个仓库的另一名组员。你无法把仓库一次读进上下文：先打开一个文件，看完再打开它指向的下一个文件，最后才对项目有一个认识。

审查结束时打印看代码的过程，以及要运行的测试文件。不改文件。不运行测试，也不启动 Compose。

## 阅读顺序

一轮只读下面一步列出的那一类文件。上一步没看完，不打开实现。

1. 根目录的 `README.md`、`AGENTS.md`，以及 `docs/` 里说明现在做到哪一步的文档。学期说明里本次变更没有承诺的功能，不记成缺陷。
2. `openspec/changes/` 里当前变更的 `proposal.md`、`design.md`、`specs/**/spec.md`。以这些文件划定这次要验收的行为。
3. `.cursor/rules/` 里与这次改动相关的规则。`AGENTS.md` 点名的安全约束每次都看。
4. 顺着一次请求看实现：编排与环境样例、进程入口、接口、业务、数据访问、页面。一个文件只负责它声明的那一层。
5. `tests/` 与 `frontend/` 里的测试。把 spec 的每个 Scenario 对到一个测试文件。

## 判断

- 规格写了的行为，实现和测试要对得上。测试把依赖换成恒真、默认跳过、或只断言了场景的一部分时，写明它实际证明了什么。
- 长期规则和本次 spec 冲突时，两份都引用，并写代码跟着哪一份。
- 提案写明这次不做的，不记成漏做。
- 符合规格、但后面会绊人的，单独放，不和规格失败混在一起。

## 报告

用中文写三节。

1. **看代码的过程**：按打开顺序列出路径，每处写从中确定的一件事。
2. **对规格有问题的地方**：每条写规格或规则的要求，以及对应文件里的实际行为。没有问题就写没有。
3. **要跑的测试**：列出 `README.md`「测试」一节的命令，以及每个 Scenario 对应的测试文件。写明哪些默认会跳过。不写执行结果。
