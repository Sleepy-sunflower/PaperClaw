# PDF 入库改为异步任务

登录、检索和阅读助手仍按学期说明的顺序做。这一份只规划后面的增强：上传 PDF 之后的切块和写入向量，改成异步任务，并用消息队列保住任务。

## 为什么放在这里

抽正文、按 400 字切块、调用嵌入接口、写入向量，比「把文件收下」长得多，可能要几十秒。这些工作如果放在同一次上传请求里，连接会一直占着，超时或进程一停，用户只看到失败。

提问不放进队列。阅读助手要在同一次连接里把回答一段一段流出来。检索和 arXiv 查询跟着这一次提问走。

## 上传时发生什么

上传接口只做三件事：确认这是当前用户的 PDF，把文件存下来，往队列放一条「请处理这篇文献」的任务。然后马上返回 HTTP 202 和一个 `task_id`。

另一个进程从队列里取任务，完成抽字、切块、嵌入和写入向量。文献库页面凭 `task_id` 查看状态：待处理、处理中、已可检索、失败。

队列负责把任务存住。停掉干活的进程后再上传，接口仍然成功，任务停在待处理。进程重新起来后继续做，不用让用户再传一次。

## 怎样算做对

- 上传的响应时间不跟着嵌入耗时变长。嵌入要很久，上传接口仍然很快返回。
- 停掉消费者后再上传，任务不丢。消费者恢复后，任务被继续执行。
- 同一份 PDF 重复上传，或同一条消息被投递两次，只留下一份文献和一套片段。可以用文件内容的摘要，或 `Idempotency-Key`，保证只处理一次。
